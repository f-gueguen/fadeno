# V1 detailed plan — secure native vertical slice

V1 delivers one authenticated CRUD application whose essential behavior works
with JavaScript disabled. This plan is dependency ordered. It does not select
public syntax before the named decision gate resolves it.

## Entry conditions

- K0-11 is merged and ADRs 0014, 0015, 0018, 0020, and 0021 are effective.
- All four experiment registry entries are `qualified` and their immutable
  evidence checks pass locally.
- The hypothesis ledger contains no active K0 claim.
- The unresolved DG-V1 gates in the decision ledger remain the only gates that
  can block their named V1 contracts; ADRs 0022 through 0024 have resolved the
  toolchain, initial-adapter, and package-boundary gates.

## Delivery checkpoints

- **Integration smoke checkpoint — V1-04:** a clean private consumer installs
  the selected package boundary and drives the adapter's Web-standard request
  contract. It proves package, install, build, and adapter boundaries without
  inventing route or renderer APIs.
- **First running framework checkpoint — V1-09:** the example serves routed,
  contextually escaped, streamed HTML through public entrypoints after all
  affected V1 contracts and the private analyzer architecture are accepted. It
  has no resource/action CRUD yet.
- **Usable V1 checkpoint — V1-13:** the authenticated CRUD example routes,
  reads, submits native forms, validates, redirects, revalidates, and handles
  expected failures without JavaScript.
- **V1 exit — V1-14:** examples, reference documentation, threat coverage,
  clean-machine workflow, and conformance suites are complete and green.

V1-DX-C uses the evolving V1 application and an isolated scenario harness. It
must execute successful, failing, correction, flow-inspection, and recovery
paths from a current packed framework through public entrypoints; normalize
unstable values; assert behavior; and source documentation snippets and outputs
from verified files. Its disposable client exercises initialize, open, edit,
diagnose, apply multiple position-dependent edits, direct and transitive
changes, regeneration, configuration reload, repair, supersession,
cancellation, close/reopen, and cleanup. The feedback workload measures the
complete edit/save-to-fresh and edit/save-to-cleared path, including
invalidation, generation, TypeScript refresh, Fadeno analysis, and final
consumer-visible state. It makes no bounded incremental-performance claim.

## H3 incremental-generation constraint

V1 may regenerate deterministic declarations cleanly and avoid rewriting
unchanged bytes. It must not claim bounded single-route incremental performance
from the K0 candidate. A later optimization slice needs a new frozen contract
and must preserve correlation, stale-output deletion, determinism, and stock-tool
behavior while meeting the locked incremental/clean target.

## V1 exit

V1 completes only when V1-13's JavaScript-disabled authenticated CRUD example
and V1-DX-C's lifecycle evidence plus V1-14's independent-user workflow pass
from a clean checkout; every V1
decision gate is resolved by an effective ADR; examples import only public
entrypoints; and current scope, specifications, traceability, diagnostics,
security evidence, and package contents agree.

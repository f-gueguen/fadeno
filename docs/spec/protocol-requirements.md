# Protocol requirements

This document defines constraints for future wire formats without freezing a
schema prematurely.

## Shared semantics

Navigation enhancement, action completion, and live updates share these
semantic requirements:

- server truth determines rendered output;
- changed output is associated with structural identity, not application
  selector commands;
- stale or duplicate messages cannot overwrite newer accepted state;
- browser, user, and island-owned state follows the preservation contract;
- errors are bounded and observable;
- a client can recover by requesting current server truth.

Sharing semantics does not require every transport to share one envelope.

## Trust boundary

Every inbound message is untrusted. Decoding validates version, shape, type,
size, identity, origin, authorization, and freshness as applicable. Unknown
required fields or unsupported protocol versions fail closed.

HTML is escaped by default. Any executable or raw markup path is explicit,
auditable, covered by content-security-policy tests, and excluded from ordinary
data interpolation.

## Lifecycle

Before an external consumer depends on a wire format, the format receives:

1. an accepted ADR;
2. an explicit version and compatibility rule;
3. positive, negative, malformed-input, replay, and ordering fixtures;
4. size and resource limits;
5. an upgrade and rollback path;
6. captured protocol examples generated by tests.

Experimental envelopes stay private and may change without migration support.

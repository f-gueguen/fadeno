# ADR 0046: Browser entrypoint package boundary

- Status: Accepted
- Date: 2026-07-20
- Owners: Fadeno maintainers
- Related specifications: [Architecture overview](../architecture/overview.md), [Build, adapters, and testing](../spec/build-adapters-testing.md), [Navigation and patching](../spec/navigation-patching-preservation.md)
- Supersedes: None

## Context

ADR 0024 keeps browser-runtime code private until a later decision and a
demonstrated consumer justify a public boundary. ADR 0045 now fixes the private
update protocol, but V2 still has no accepted path from a built application to
optional browser enhancement. Adding implementation first would make an
accidental source path, root re-export, or separately versioned browser package
the compatibility contract.

V2-01A therefore decides only the package and loading boundary. A disposable
package proves that a clean consumer can resolve the proposed topology from a
tarball while the real published package remains unchanged. V2-02 separately
owns the first implementation, concrete exported symbols, Changeset, security
evidence, and clean current-package consumer.

## Decision drivers

- Keep one logical package and one release identity.
- Keep browser-only code unreachable from the neutral root and Node adapter.
- Make enhancement optional and preserve a complete no-JavaScript document.
- Load only framework-owned generated bytes under the renderer's existing nonce
  authority.
- Avoid freezing browser-runtime symbols before an implementation demonstrates
  them.
- Prove package resolution and deep-import refusal from an installed tarball.

## Decision

The existing `@fadeno/framework` package will add exactly one public
`./browser` subpath when V2-02 implements the browser runtime. No second package,
alias, wildcard export, browser condition on `.`, or browser re-export from
`.` or `./node` is accepted. The subpath is an explicit browser-only facade;
its private implementation may depend inward on Web-platform helpers and the
accepted private update decoder. It cannot depend on Node built-ins, server,
compiler, analyzer, application source, or private package deep imports. The
neutral root and Node graphs cannot depend on or dynamically load it.

The application build owns a generated browser module that statically imports
`@fadeno/framework/browser`. Authored application code does not name private
browser files. A rendered document opts into enhancement only by emitting that
built module through the framework-owned external module-script path with the
same request-owned CSP nonce authority already selected for framework
executable markup. Importing the future facade alone has no implicit global
startup side effect; V2-02 must demonstrate the minimum explicit bootstrap
symbol before that symbol becomes public. Missing JavaScript, blocked loading,
an absent or wrong nonce, unsupported protocol compatibility, or any refused
boundary leaves native links and forms authoritative.

Browser and server artifacts share the framework package version and one
application build identity. There is no separately negotiated browser-package
version. The private update envelope retains its own exact compatibility
version from ADR 0045 and is rejected independently. A browser artifact from a
different package or application generation cannot apply an update.

V2-01A does not add `./browser` to the real package manifest. Its disposable
sentinel package exposes exactly `.`, `./node`, `./jsx-runtime`, and
`./browser`, is packed and installed outside the workspace, and is consumed
through a side-effect-free `./browser` module resolution. The proof also keeps
a browser-private canary in the tarball while TypeScript and runtime deep
imports are refused. The current public package is checked to retain only its
three existing subpaths until V2-02 supplies implementation and release intent.

## Alternatives considered

- A separate browser package: rejected because browser and server bytes form
  one framework/application generation and no independent owner exists.
- A `browser` condition on the root export: rejected because resolution would
  silently change the neutral root graph and make environment selection
  tool-dependent.
- Re-export browser startup from `.`: rejected because server and Node
  consumers would gain browser reachability.
- A wildcard or private deep import: rejected because internal organization
  would become compatibility surface.
- An import-for-side-effects bootstrap: rejected because merely resolving a
  package must not unexpectedly take document ownership.
- Fix concrete startup symbols in this decision: rejected because V2-01A has
  no runtime implementation capable of demonstrating their semantics.

## Consequences

- V2-02 may implement only `@fadeno/framework/browser` inside the existing
  package and must add one reviewed Changeset for that user-visible export.
- The public browser symbol surface remains undecided until V2-02 demonstrates
  it through the real renderer, generated application module, and packed
  consumer.
- Native rendering, links, and forms remain complete when the browser artifact
  is absent or refused.
- Rollback before V2-02 removes this decision and disposable proof with no
  package migration. After release, operational rollback stops emitting the
  generated module and browser artifact; removing the public subpath requires a
  separately versioned compatibility decision.
- Release impact is none: V2-01A changes no package bytes, exports, version, or
  behavior, so it carries no Changeset.

## Validation

`pnpm check:v2-browser-entrypoint-boundary` verifies the accepted documentation
and package model, compiles the browser-only prototype without Node types,
packs and installs the disposable package outside the workspace, resolves its
exact `./browser` export, proves its root and Node outputs do not reference the
browser module, and refuses browser-private deep imports in TypeScript and at
runtime. Mutation tests remove or weaken the exact subpath, dependency,
loading, compatibility, rollback, and unchanged-public-package controls.

`pnpm check:v2-plan`, `pnpm check`, and `pnpm ci:local` retain the complete
native, package, decision, documentation, and security baselines.

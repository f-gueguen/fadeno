# ADR 0039: Public project creation

- Status: Accepted
- Date: 2026-07-18
- Owners: Fadeno maintainers
- Related specifications: [Build, adapters, and testing](../spec/build-adapters-testing.md), [Security requirements](../security/requirements.md)
- Supersedes: None

## Context

ADR 0011 requires independently usable project creation but deliberately left
the exact command open until the vertical slice and package boundary existed.
A0-04 must now expose one reproducible path from the installed public package
to a project that uses the same compiler, analyzer, adapter, and runtime as the
canonical application.

## Decision drivers

- Project creation must be non-interactive and reproducible for people, agents,
  documentation, and clean-machine tests.
- The command must never overwrite existing work or escape its declared root.
- Generated source must use only public package entrypoints and stock
  TypeScript/JSX.
- The scaffold must remain small while demonstrating a real routed document,
  native external CSS, checking, building, development, and production start.

## Decision

The existing `fadeno` executable owns one public creation form:

```sh
fadeno create --project-root ./my-fadeno-app
```

The form is exact and non-interactive. The project root is explicit, its final
parent already exists, every existing parent-path component is an ordinary
non-symlink directory, the target does not exist, and the final directory name
is a lowercase unscoped package name matching `[a-z][a-z0-9-]{0,63}`. Unknown,
duplicate, missing, or additional arguments are usage refusals.

Creation prepares every output byte before writing, atomically claims the
missing target with exclusive directory creation, and writes a fixed allowlist
only inside that framework-owned directory. Every file path is relative,
normalized, and contained. Any later failure removes the directory the command
claimed and leaves the target absent. Existing targets, symlinked parent-path
components, non-directory parents, and invalid names are refused without
writes. The command does not install dependencies, initialize version control,
contact a network, execute generated code, or overwrite a partial or existing
project.

The generated manifest pins the exact version of the executing
`@fadeno/framework` package. It exposes only `check`, `build`, `dev`, and
`start`; A0-05 owns the first supported application-test command. The template
is a bounded, action-free subset of the canonical tested application: typed
configuration, layout, page, not-found page, and application-owned same-origin
external CSS. It does not create a second compiler or runtime.

## Alternatives considered

- Interactive prompts: rejected because their answers and terminal behavior
  are harder to reproduce and automate.
- Positional destination arguments: rejected because existing public commands
  already make project-root ownership explicit.
- Sibling staging followed by ordinary rename: rejected because the available
  rename operation may replace an empty directory created concurrently; an
  exclusive target-directory claim preserves the stronger no-overwrite rule.
- Create into an existing empty directory: rejected because emptiness checks
  race and make rollback ownership ambiguous.
- Install dependencies automatically: rejected because project creation must
  not execute package-manager lifecycle code or require network access.
- Ship a simplified scaffold runtime: rejected because it would drift from the
  production package and compiler.

## Consequences

- A created project needs an explicit package-manager install before its
  commands run.
- The exact package pin makes the generated source reproducible and ties it to
  the CLI that created it; upgrades remain explicit pre-1.0 changes.
- Users choose a different directory name before creation rather than asking
  the command to sanitize an unsafe package identity.
- A later template variant, prompt, package manager, or existing-directory mode
  requires demonstrated need and a superseding decision.

## Validation

`pnpm check:a0-create` builds and packs the current public package, invokes its
installed executable, compares every generated byte to tracked normalized
evidence, installs the same packed package into the created consumer, and runs
check/build/dev/start. It also proves usage, invalid-name, existing-target,
symlink-parent and symlink-ancestor refusal, injected-write-failure, cleanup,
retry, path containment, and byte-stability controls. Documentation snippets
come from the executed created project.
